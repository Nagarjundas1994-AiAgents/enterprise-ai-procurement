Part 1 · Concepts

What is a CAP plugin, really?

A beginner meets three different things that all get called “plugin”. They are not the same:

CAP Framework (@sap/cds runtime + cds-dk tooling) ↓ declares a reusable slice of capability CAP Facet — e.g. cds add hana ............ (project setup step) ↓ implemented as code in cds-dk via the cds.add Plugin API cds add Plugin — e.g. built-in 'hana' ... (runs once, writes files) ↓ OR a runtime package you install cds-plugin (Node.js) — e.g. npm add @cap-js/audit-logging ↓ auto-loaded via cds-plugin.js + auto-configured via package.json cds section BTP Service Integration — e.g. SAP Audit Log service instance + binding ↓ your code on top Custom Extension — your handlers, annotations, custom plugins
🧩 cds add hana = a facetA one-time project generator. It edits package.json, adds mta.yaml resources, wires cds.requires.db. It does not run in production.
📦 npm add @cap-js/audit-logging = a pluginA runtime package. Its cds-plugin.js is auto-detected and its cds section in package.json auto-configures your app on every boot.
☁️ SAP Audit Log service = a BTP serviceThe platform backing service. The plugin talks to it (via binding) in production and to the console locally. Three layers, one story.
🔌 Your extension = custom codeHandlers, annotations, own cds-plugin.js packages, own cds add plugins (Part 32). Same techniques SAP uses.
Version / compatibility legend used everywhereBadges on every card: Node.js Java n/a planned / verify. “CF-only” means the managed-service wiring generated by the facet targets Cloud Foundry. Statuses: Official (in cds-dk or cap-js/cap-java), Community, Experimental/Beta, Deprecated.

Part 4 · Security

Security & identity plugins

XSUAA — OAuth2 scopes on Cloud Foundry

Flow: approuter login → JWT with xsappname.scope entries → CAP validates signature + tenant → @restrict checks scopes. Role templates live in xs-security.json; role collections are assigned in the cockpit.

IAS — who logs in

Browser → IAS (corporate IdP, MFA) → XSUAA (scopes) → CAP → User

Use IAS when humans must log in with company credentials. IAS authenticates; XSUAA still authorizes. Configure IAS→XSUAA trust and map IAS groups to role collections.

AMS — centralized authorization

AMS evaluates policies at runtime instead of hardcoding every rule in @restrict. Use it when rules change often, need audit, or span apps. Difference: @restrict = static model-level guard; AMS = dynamic policy decision per request (with deny-by-default + short-TTL caching).

Part 5 · SaaS

Multitenancy

Provider subaccount (your app + SaaS registry) ├── Tenant A (own HDI container / isolated data) ├── Tenant B └── Tenant C (subscribe → onboard → use → offboard)

cds add multitenancy wires the SaaS registry and (Node.js) the MTX sidecar for tenant lifecycle. Tenant identity always comes from the JWT/service binding — never from client input. Legacy MTX APIs are marked legacy in CAPire: prefer the current sidecar/subscription model and test subscribe → use → upgrade → unsubscribe end-to-end.

Part 6 · SaaS

Extensibility

Base application (your model + services) ↓ allowlisted extension points Extension project (cds pull → extend → cds push) ↓ Customer model + behavior, upgrade-safe

Pair with cds add multitenancy. Workflow: cds pull the base model, add customer fields/logic in a separate extension project, cds push back. Rules: allowlist extendable entities, validate extension models in CI, and re-test upgrades with extensions applied.

Part 7 · Rollouts

Feature toggles

DisciplineEvery toggle gets an owner and an expiry date; enforce server-side (never trust client gating for paid features); delete the toggle once fully rolled out.

Part 10 · Deep dive

CAP + Apache Kafka

CAP producer → Kafka topic (partitions) → consumer group → CAP handler (serialization contract · retention · replay)

Local Kafka via Docker; production via provider-managed Kafka. Per-topic decisions: serializer (CloudEvents JSON recommended), partitions vs ordering needs, retention, one consumer group per landscape, retry + DLQ topics, lag monitoring.

Part 11 · Status note

Redis messaging

cds add redis-messaging wires Redis pub-sub (Cloud Foundry only). Purpose: low-latency fan-out where Redis already exists. Limits: not a durable enterprise queue replacement; confirm the support status in your cds-dk version (cds add --help). Set eviction/persistence deliberately and never assume Kyma support.

Parts 21–26 · Productivity

data · http · handler · test · typer · esm

  • data: cds add data --filter Books --records 5 --content-type json — small, meaningful seeds; gitignore dumps.
  • http: cds add http --filter CatalogService — mock-user files stay local; --for-app for remote JWT.
  • handler: generate stubs, delete what you don’t customize.
  • test: no built-in facet — use @cap-js/cds-test (Node) / Java test tooling, run in CI.
  • typer vs typescript: typer generates model types (#cds-models); typescript facet sets up TS handlers. Use both for typed TS apps.
  • esm vs cjs: CJS is default; cds add esm switches to import/export — audit deps first.

Parts 29–30 · Kubernetes

Kyma + CAP Operator

CAP source → containerize → helm chart → CAP Operator CRs → K8s (multitenant lifecycle) values.yaml + values.schema.json (providerSubaccountId, NOT globalAccountId)

cds add kyma gives API Rules and base resources; npm add @cap-js/cap-operator-plugin -D + cds add cap-operator generates the Operator’s custom resources so you don’t hand-write Helm CRs. Keep the chart generated-then-reviewed; helm lint + template diffs in CI.

Part 31 · CI/CD

Pipeline

Git → Build (mbt/helm) → Test (unit+integration) → Security (lint, audit) → Deploy (CF/Kyma) → Monitor

cds add pipeline scaffolds the descriptors (e.g. GitHub Actions). Secrets come from vaults, never YAML; quality gates (tests, lint, cds deploy dry-run) block bad builds before they reach BTP.

Part 32 · Build your own

Custom cds add plugin development

cds-plugin.js → register(name, impl) → run() writes files → combine() merges configs → options() CLI flags → requires() deps

Every method: register names the facet; run writes/generates files; combine merges into existing configs (package.json, mta.yaml); options declares CLI flags; requires lists facets that must run first (e.g. xsuaa).

Part 33 · Build your own

The cds-plugin technique

npm package → cds-plugin.js in root → CAP auto-detects (deps with that file) → merges package.json cds section (auto-config) → loads module on lifecycle events

Distribution: publish to npm; consumers npm add it and get behavior with zero wiring. Production rules: version conservatively, namespace your cds.requires keys, never mutate other plugins’ config.

Part 34 · Java

CAP Java plugins

Maven dependency (jar, runtime scope) → CAP Java runtime → model + behavior contributed

Differences that matter: Java plugins ship config via Spring Boot conventions (cds env shows design-time only); messaging/AI plugins may lag Node (see badges); H2/Liquibase are Java-first. Always check the Java column before planning.

Part 46 · Operate

8-step installation guide (every plugin)

  1. Install — npm add <plugin> or add the Maven dependency.
  2. Run cds add — cds add <facet> for project wiring.
  3. Inspect — git status/diff: know every touched file.
  4. Configure — profiles for local vs production kinds.
  5. Run locally — cds watch with mocks/consoles.
  6. Test — unit + integration, incl. failure paths.
  7. Deploy — bind real services, verify in cockpit.
  8. Monitor — logs, metrics, queue depth, audit viewer.
