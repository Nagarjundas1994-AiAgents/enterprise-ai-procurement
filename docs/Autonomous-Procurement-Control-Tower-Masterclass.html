The one rule, repeated all course

An AI agent never touches the database directly. It calls a governed CAP service. CAP owns business logic and authorization. MCP, A2A and the gateway are how agents reach that governed layer — never a way around it. Every diagram below is a variation on that sentence.

MODULE 01

The business problem

What is it? The scenario

Autonomous Procurement Control Tower is a realistic enterprise procurement platform. A factory buyer raises a purchase requisition (I need 500 brake pads), a manager approves it, the system converts it to a purchase order against a supplier, tracks goods receipts, invoices and payments, watches budgets, and flags risks (late delivery, abnormal price). Then AI arrives: buyers ask questions in plain English, a procurement agent answers using governed tools, and a risk agent supplies risk analysis over A2A.

Requisitions to payment

PR with items, approvals, PO with items, receipts, invoices, payments — the document flow auditors actually check.

Master data + money

Suppliers with risk scores, materials, departments, budgets with committed and consumed amounts.

Risk + policy

RiskAssessments, Policies as data, PolicyViolations — policy gates decide, the LLM only recommends.

Agents + audit

Agents, AgentExecutions, MCPTools, MCPToolExecutions, AIConversations, AuditLogs — every AI action traceable.

Why do we need it? The pain today

  1. Buyer emails spreadsheets; nobody knows the PR status or remaining budget.
  2. Manager approves by gut feel; no policy check, no risk score, no audit proof.
  3. Invoice arrives for a different amount; 3-way match (PO vs receipt vs invoice) is manual.
  4. Supplier keeps delivering late; the signal hides in past orders nobody queries.
  5. Leadership asks 'which suppliers are risky?' — the answer takes a week of SQL.

User asks

Which suppliers have high procurement risk, and why?

Governed answer (end of course)

Risk Agent scores suppliers from live POs, receipts and disputes via MCP tools — with policy citations and an audit row — instead of a week of SQL.

User asks

Create a requisition for 200 brake pads and route it for approval.

Governed action

Procurement Agent calls createPurchaseRequisition + submitForApproval through the MCP gateway — RBAC, tenant check, budget check, audit write — then shows the approval task.

Common mistake

Building 'a chatbot with direct database access'. It demos well and fails the first audit: no authorization, no tenant isolation, no policy gate, no trace of who approved what. This course builds the opposite — the agent is the least privileged actor in the system.

Is this a real working project or disconnected demos?

One project, extended phase by phase. Phase 4's OData URLs still work in Phase 33's BTP deployment.

Do I need a paid LLM key?

No. Local development uses a MockLLM provider with deterministic responses. Real providers (SAP AI Core / Generative AI Hub) plug in later behind the same interface.

Do I need BTP on day one?

No. Everything runs locally (SQLite/Postgres, mocked auth, mock LLM, mock destination) until the deployment phases.

How a Solution Architect thinks about this

The mindset shift

Novice approach

"I will add an AI agent, an MCP server, and A2A to my app." Technology list first — authorization, tenancy and audit discovered during the incident review.

Architect approach

"The capability is governed procurement execution. The system of record is CAP + Postgres. Agents reach it through tools with explicit grants, every write audited, every cross-agent call authenticated. Then I pick protocols." Capability, owner, failure mode first.

Architect insight

For every box in any AI architecture diagram, ask: who calls it, with whose identity, checked against what policy, and where is the audit row? If any answer is 'the agent just can', the diagram is a demo, not a design.

STEP 05

Phase 2 — Domain model with CDS

WHAT WE HAVE: empty db/. ADDING NOW: 30+ entities with compositions, tenant isolation, status enums, concurrency versions.

What is it?

Simple. CDS is the blueprint of your business: what things exist (Supplier, Order) and how they relate — before any screens or code.

SAP-specific. CDS compiles to OData V4 + SQL. One model drives the API, the DB schema, and Fiori annotations.

Technical. Namespace + entities + associations/compositions + managed/cuid aspects + types + @assert constraints. Compositions own children (items die with parent); associations reference independent entities.

ConceptUsed whereWhy
cuid, managedEvery entityUUID key + createdAt/modifiedAt/createdBy free
CompositionPR-items, PO-items, contacts, messagesChildren owned; cascade delete
Associationsupplier, requester, departmentIndependent master data referenced
version IntegerPR + POOptimistic concurrency: WHERE version = expected
@assert.uniquerequisitionNo, orderNo, supplierIdDB-level duplicate guard

Production note

HANA Cloud needs no model change — only the db.kind + deploy target change (Phase 6). Keep CDS portable: no Postgres-only types.

STEP 07

Phase 4 — OData V4 service

HAVE: tables. ADDING: typed HTTP API with actions for every state change.

What is it?

OData V4 is the typed HTTP contract CAP generates from your service definition: entities become URL-addressable sets with $filter/$expand/$orderby, actions become POST endpoints. Our paths: /odata/v4/procurement, /catalog, /supplier, /invoice, /approval, /mcp, /agents.

ID params are String, not UUID

OData URL parsing nulls non-GUID values for UUID-typed params → phantom 404s with readable seed IDs. This repo types every action/function ID param as String deliberately. OData function params need parenthesis syntax /fn(p='v'), never ?p='v'.

VerbExampleMeaning
GET/PurchaseRequisitionsList (tenant-filtered)
GET/PurchaseRequisitions(ID)One row + $expand=items
POST/PurchaseRequisitionsCreate (before CREATE validates)
PATCH/PurchaseRequisitions(ID)Partial update (version-checked)
POST/submitRequisitionUnbound action via .send(), never .run({action}) cross-service
STEP 08

Phase 5 — Complete CRUD

HAVE: OData surface. ADDING: validation, tenancy, RBAC and audit on every read/write.

CAP already gives you CRUD — customize at the edges

Generic handlers serve CREATE/READ/UPDATE/DELETE. You add before/after hooks only for validation, defaults, tenancy and audit. State changes (submit/approve/convert) are actions, not raw PATCHes, so transitions are explicit and auditable.

HookUse forNever for
before CREATE/UPDATEValidation, defaults, tenant stamping, permission checkCross-entity writes (use actions + tx)
after CREATEAudit, notifications (try/catch, return data)Throwing — it would break the response
on State transitions with tx + version check + auditSilent PATCH status edits

after-hook trap

An after hook that returns undefined wipes the response body. Always return data. Wrap audit in try/catch — observability must never break the business path.

Phase 7 — Authentication + authorization

HAVE: open API. ADDING: identity, 9 role collections, empty-by-default AI_AGENT, tenant isolation.

What is it?

Simple. Authentication = who are you (badge check). Authorization = what may you do (which doors your badge opens).

SAP-specific. Locally: x-mock-user + x-agent-id headers. BTP: IAS login → approuter → XSUAA JWT with scopes → CAP checks scopes.

Technical. lib/auth/authentication.ts builds ctx {userId, tenantId, roles, isAgent}. AuthorizationService.requirePermission maps scopes→PERMISSIONS. Tenant always comes from ctx, never req.data.

STEP 14

Phase 11 — MCP from zero

HAVE: no AI surface. ADDING: mental model + vocabulary (host/client/server/tools/resources/prompts/transport).

What is it?

Simple. MCP is a waiter's notepad: the AI (customer) writes structured orders (tool calls); the server (kitchen = CAP) cooks only what's on the menu (allowed tools) and bills with a receipt (audit).

SAP-specific. Our MCP layer exposes 13 CAP capabilities as tools. The agent never writes SQL — it calls searchSuppliers, checkBudget, createPurchaseRequisition, never INSERT.

Technical. MCP = JSON-RPC 2.0 over HTTP/SSE: Host (app) → Client (connection) → Server (tools/resources/prompts). Tools have inputSchema/outputSchema. Transports: Streamable HTTP (prod), stdio (local dev). VERIFY transport field names against current @cap-js/mcp docs.

User identity ≠ agent identity ≠ tool permission. The JWT carries the user; x-agent-id carries the agent; AgentToolPermissions + scopes carry what this (user, agent, tool) triple may do. MCP itself authorizes nothing — it transports identity to CAP, which decides.

ADR-007MCP is transport, CAP is authority
Context

An agent runtime naturally wants to 'just call the DB'.

Problem

Where to enforce tool authorization?

Options considered
  • Trust the agent/prompt. Prompt injection becomes privilege escalation.
  • Enforce in CAP per call. Deterministic, testable, auditable.
Decision

Both gateway (menu filtering, rate limits) AND CAP (scope + grant + policy + audit) enforce; CAP has the final word.

Why

Defense in depth; gateway stays dumb-fast.

Trade-offs

Two places to keep in sync — mitigated by generating the gateway menu from MCPTools + grants.

Consequences

A compromised agent gets an empty menu and DENIED rows, not data.

HAVE: one agent. ADDING: two agents, discovery doc, authenticated task exchange.

AI agent security — the delegation model

Authorizing what an agent can do (the critical section)

User identity ≠ agent identity ≠ tool identity. A manager delegating to procurement-agent for a €200k approval still fails unless: the user holds APPROVE_PR, the agent holds an explicit grant for the approval path, the amount is under maxAmount, and policy returns AUTO_APPROVE (higher bands route to REQUIRE_MANAGER / FINANCE / HUMAN).

Dual control: the agent drafts and routes; a human manager approves in UI5. An auto-approving agent would collapse the REQUIRE_MANAGER/FINANCE/HUMAN bands.
