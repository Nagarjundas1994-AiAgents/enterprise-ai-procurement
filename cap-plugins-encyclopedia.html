Part 1 — What is a CAP plugin? (read this first)

Beginner mental model: cds add hana ≠ npm add @cap-js/audit-logging ≠ SAP BTP service. They are three layers that work together.

CAP Framework (@sap/cds runtime + cds-dk CLI) ↓ CAP Facet (a named capability, e.g. "hana", "xsuaa", "mta") ↓ cds add Plugin (generator that writes config/files for the facet) ↓ cds-plugin (Node.js auto-loaded runtime package via cds-plugin.js) ↓ BTP Service Integration (binding + entitlement, e.g. Audit Log service) ↓ Custom Extension (your code on top)
ConceptExampleWhat it does
Facetcds add hanaProject generator: adds deps + mta.yaml + profiles in package.json.
cds-plugin (npm)npm add @cap-js/audit-loggingRuntime extension auto-loaded via cds-plugin.js. Logs to console locally, to BTP service when bound.
BTP serviceAudit Log service instanceThe actual cloud backing service (entitlement + instance + binding).

Rule: Facet = scaffolding. Plugin = runtime behavior. BTP service = cloud resource. You usually need facet + plugin + binding together in production.

Part 3b — Database deep-dives (per database: transactions · performance · limitations)

SAP HANA Cloud — @cap-js/hana / cds-feature-hana (production)

Architecture: CAP → HANA adapter (hdb driver — do NOT add hdb/@sap/hana-client yourself) → HDI container → HANA Cloud. Deploy format hdbtable/hdbview via cds build --for hana; custom artifacts in db/src.

cds add hana
npm add @cap-js/hana
cds build --for hana
cds deploy --to hana --production
# hybrid local test: cds add hana --for hybrid + cds bind -2 hana:<instance>

Transactions: full ACID; one CAP request = one DB transaction (rollback on req.reject). Performance: native HANA associations, column store, $expand pushed down; add indexes in db/src/*.hdbindex. Limitations: HDI never deletes artifacts on undeploy (keep db/undeploy.json); type changes need manual ALTER resolve; trial DBs sleep daily.

SQLite — @cap-js/sqlite (development only) 
npm add @cap-js/sqlite -D
# package.json: cds.requires.db [development] {kind:'sqlite', impl:'@cap-js/sqlite', credentials:{url:'memory'}}

Transactions: single-writer; fine for cds watch/test. Performance: in-memory = fastest iteration. Limitations: NOT for production; dialect differs from HANA (verify native queries on HANA before release); no HDI/HDB artifacts.

PostgreSQL — @cap-js/postgres (community + CAP team) 
# docker local: image postgres:alpine, POSTGRES_PASSWORD=postgres, 5432:5432
npm add @cap-js/postgres
# production: managed PostgreSQL (hyperscaler/BTP); configure via cds.requires.db + service binding

Transactions: full ACID MVCC. Performance: strong for open-source landscapes; pooling via binding. Limitations: no HDI; HANA-specific CDS (spatial, native assoc.) may not port; check adapter release vs your @sap/cds major.

H2 (Java local) + Liquibase (Java versioned migration) 
<!-- H2: local/test scope only (srv/pom.xml) -->
cds add liquibase   # generates db/changelog/* versioned migrations for CF/Kyma Java deploys

Transactions: H2 in-memory/file for tests. Liquibase: every schema change = reviewed changelog (diff, rollback, checksum); mandatory for audited Java production landscapes. Limitation: changelog drift if anyone edits the DB directly — always change the model first.

Part 4 — Security & identity (xsuaa · ias · ams)

XSUAA — cds add xsuaa (OAuth2/JWT, scopes, role templates/collections) 
cds add xsuaa
# generates: xs-security.json (scopes, role-templates), mta.yaml resource (xsuaa),
# package.json auth config. Then: cds bind / mbt build + cf deploy, create role collections in BTP cockpit.

AuthN via JWT (XSUAA broker), AuthZ via @requires/@restrict matching scopes. Mistakes: forgetting role-collection assignment; scope name mismatch; testing prod APIs with mock users.

IAS — cds add ias
CAP → SAP Identity Authentication (IAS, OIDC) → User Use when: human SSO, IAS as IdP (often with XSUAA broker), app-to-app via IAS.
AMS (Authorization Management Service)

Centralized authorization policies (attributes, policies) vs local @restrict. Use when policies must be managed outside code, shared across apps, audited centrally. @requires/@restrict = code-level; AMS = policy plane that CAP evaluates at runtime.

Part 8b — Messaging deep-dives (per broker: protocol · auth · topic/queue · producer/consumer)

local-messaging + file-based-messaging (development) 
cds add local-messaging        # in-process: emit + on, no infra
cds add file-based-messaging   # file outbox: survives restarts, inspectable JSON
// same handler code runs unmodified against EM/Kafka in production:
srv.on('PurchaseOrder.Approved', async msg => { /* msg.data, msg.headers (CloudEvents) */ });

Protocol: in-memory / file outbox. Auth/topics: none (dev only). Use: TDD for handlers, offline work, CI without brokers.

enterprise-messaging / event-mesh (+ -shared) (Cloud Foundry production) 
cds add enterprise-messaging   # dedicated broker instance
# -shared variant binds the shared EM service instance instead
# package.json: cds.requires.messaging {kind:'enterprise-messaging'}
# topics/queues + subscriptions created in EM cockpit; CloudEvents envelope automatic

Broker: SAP Enterprise Messaging / Event Mesh (CF). Auth: EM management + messaging credentials from binding. Topics/queues: namespace per landscape; dead-letter queues + retries configured in cockpit. Node + Java: both supported. Kyma: prefer K8s-native options (Kafka/AEM) over CF EM.

Kafka (high-throughput / non-SAP landscapes) 
cds add kafka
# cds.requires.messaging {kind:'kafka'} — brokers, SASL/TLS, group.id per landscape
# payload: JSON CloudEvents; dedicated DLQ topic per consumer group

Broker: Apache Kafka topics (partitions scale consumers). Local: docker Kafka. Prod: managed Kafka on CF/Kyma. Serialization: JSON CloudEvents; schema-registry where enforced. Errors: retry with backoff → DLQ topic → alerting.

Event Hub (consume S/4 events) + Advanced Event Mesh (enterprise mesh) 
npm add @cap-js/event-broker        # consume S/4HANA Cloud events via Cloud Application Event Hub
npm add @cap-js/advanced-event-mesh # Integration Suite AEM (Solace-backed) for non-SAP systems
const S4 = await cds.connect.to('API_BUSINESS_PARTNER');
S4.on('BusinessPartner.Changed', msg => { /* ... */ });

Auth: service bindings (event-hub / AEM). Local test: mock broker profile; prod: cockpit-managed topics/queues. Java: cds-feature-event-hub / cds-feature-advanced-event-mesh.

Part 32 — Build your own cds add plugin (CRITICAL)

API: cap.cloud.sap/docs/tools/apis/cds-add. Lifecycle: register() → run() → combine() → options() → requires().

// my-cap-plugin/package.json: { "name": "my-cap-plugin", "cds-plugin": "./cds-plugin.js" }
// my-cap-plugin/cds-plugin.js
const cds = require('@sap/cds-dk');
cds.add.register('my-feature', require('./lib/add'));
// my-cap-plugin/lib/add.js
module.exports = class extends cds.add.Plugin {
  async run() { // scaffold: copy templates, add deps
    const { copy } = this; await copy('files/pg.yaml').to('pg.yaml');
  }
  async combine() { // integrate when OTHER facets run (mta/kyma/xsuaa/mtx present?)
    const { readProject, merge } = cds.add;
  }
  options() { return { out: { type: 'string', help: 'output dir' } }; }
  requires() { return ['xsuaa']; } // facet prerequisites
};

Checklist: don't do build work in add; use merge().into() + registries + mvn.add() utils; test via cds add my-feature --dry-style runs.

Domain model + service

// db/schema.cds
using { Attachments } from '@cap-js/attachments';
using { cuid, managed } from '@sap/cds/common';
namespace procurement;
annotate PurchaseOrders with @PersonalData:{DataSubjectRole:'Buyer',EntitySemantics:'DataSubject'};
entity PurchaseOrders : cuid, managed {
  supplier   : String;
  total      : Decimal(15,2);
  status     : String default 'Draft';
  buyerEmail : String @PersonalData.IsPotentiallyPersonal;
  attachments: Composition of many Attachments;
}
// srv/procurement.cds
using procurement from '../db/schema';
service ProcurementService @(requires:'authenticated') {
  @restrict:[{grant:['READ','CREATE'],to:'Buyer'},{grant:'*',to:'Approver'}]
  entity PurchaseOrders as projection on procurement.PurchaseOrders
    actions { action approve(); };
  event PurchaseOrder.Approved { poID: String; total: Decimal; };
}

Handler (approve → emit → notify → audit-covered)

// srv/procurement.js
const cds = require('@sap/cds');
module.exports = class ProcurementService extends cds.ApplicationService {
  async init() {
    const LOG = cds.log('procurement');
    this.on('approve', 'PurchaseOrders', async req => {
      const { ID, total } = await SELECT.one.from('procurement.PurchaseOrders', req.params[0]);
      await UPDATE('procurement.PurchaseOrders', req.params[0]).with({ status: 'Approved' });
      await this.emit('PurchaseOrder.Approved', { poID: ID, total });
      const alert = await cds.connect.to('notifications');
      await alert.notify({ recipients: ['purchasing-team'], title: 'PO ' + ID + ' approved', description: 'Total ' + total });
      LOG.info('PO approved', { po: ID });
      return { ID, status: 'Approved' };
    });
    this.on('PurchaseOrder.Approved', msg => LOG.info('consumed approval', msg.data));
    return super.init();
  }
};
