0.1 · The app in plain English

Imagine an office where people request things to buy (laptops, chairs). This backend is the rule-keeping computer behind that process:

  • Employee Ravi writes a request: "15 laptops, ₹12,75,000" → saved as DRAFT.
  • Ravi clicks submit → request becomes SUBMITTED and lands on a manager's desk.
  • Approver Meera checks the budget and approves → APPROVED (or rejects with a reason).
  • Procurement officer Kiran converts it into a purchase order sent to a supplier.
  • The supplier delivers goods (goods receipt), sends an invoice; the system matches invoice vs order vs delivery (three-way match); finance pays.
  • AI agents are junior assistants that can look things up and draft orders — but every click they make passes the same permission checks as a human, and expensive/risky actions need a human to say yes (policy engine).
  • Everything important is written into an audit log — who did what, when, on whose behalf.

0.2 · Words you'll see everywhere (30-second versions)

  • CAP — SAP's framework for building business backends. You are reading the docs of an app built with it.
  • CDS — the language CAP uses to describe data (like a blueprint: "a purchase order has a number, a supplier, items…"). Lives in db/*.cds.
  • Service / OData — the doors through which the outside world talks to the data (web addresses starting with /odata/v4/…).
  • Handler — TypeScript code (srv/*.ts) that runs when someone knocks on a door: checks permission, applies rules, saves to DB.
  • RBAC — "role-based access control": your role (employee, manager…) decides what you're allowed to do.
  • Tenant — one customer company sharing the same app (Acme India vs Acme EU). The app guarantees they never see each other's data.
  • MCP — a standard plug that lets AI assistants (like OpenCode) use your app's functions as tools.
  • A2A / agents — autonomous helpers that call those tools to do multi-step jobs (check budget → check supplier → create order).
  • Policy engine — the table of money limits that decides "auto-ok" vs "needs a human". Not the AI — a boring, predictable table. That's the point.
  • Audit log — the tamper-evident diary of every sensitive action.
Rule of the whole system, in one sentence: nobody — not a manager from another department, not another tenant, not an AI agent — can do anything except through a door that checks who they are, what they're allowed, and whether policy permits it, and every sensitive action is written down.

1 · Vision & Goals

A realistic enterprise procurement platform — not a CRUD demo — where humans, REST clients, MCP clients and autonomous AI agents all consume the same backend through the same authorization model.

  • Purchase requisitions → manager approvals → purchase orders → suppliers → goods receipts → invoices → payments.
  • Seven specialized AI agents plus an orchestrator, exposed via A2A, acting only through permission-checked CAP services.
  • Six MCP chat servers for OpenCode / Claude / Joule style MCP clients — one curated (/mcp/procurement, 13 tools) plus five domain servers (/mcp/catalog, /mcp/procurement-ops, /mcp/suppliers, /mcp/approvals, /mcp/invoices).
  • Non-negotiable guarantees: tenant isolation, RBAC on every path, policy-gated automation, full audit trail, no secrets in code/logs.

T · Step-by-Step Tutorial — Zero to Running (Beginners)

Do these in order. Each step says what to type, what you should see, and what just happened. All commands run from the enterprise-ai-procurement folder.

Prerequisites (one-time)

  • Install Node.js 20+ (node --version to check).
  • Install CAP tooling once: npm i -g @sap/cds-dk (then cds --version).
  • Optional: Docker Desktop (only if you want real PostgreSQL locally); OpenCode (only for the MCP chapter).

Step 1 — Install dependencies

npm i

Expect: lots of downloading, ends with no red errors. What happened: the libraries from Section 2 landed in node_modules/.

Step 2 — Check the code is healthy (before running anything)

npx tsc --noEmit        # TypeScript typecheck — expect silence + exit 0
npx cds compile db srv --to csn   # CDS model compile — expect a big JSON dump, no [ERROR]
npm test                # 26 tests (23 security incl. XSUAA mapping + 3 unit), all green
Newbie tip: if tsc complains about srv/server.js being overwritten — that's already fixed via "noEmit": true in tsconfig.json. This project never emits compiled JS; tsx runs TypeScript directly.

Step 3 — Start the backend

npm start

Expect: lines like init from db\data\…csv, then serving CatalogService { at: ['/odata/v4/catalog', '/mcp/catalog'] … } for 8 services, then server listening on { url: 'http://localhost:4004' }. What happened: seed data loaded into an in-memory database; 8 services are live, 6 of them dual-served over MCP (/mcp/catalog, /mcp/procurement-ops, /mcp/suppliers, /mcp/approvals, /mcp/invoices, /mcp/procurement). Leave this window running.

Step 4 — Is it alive? (new terminal window)

curl localhost:4004/health        # → {"status":"UP"}
curl localhost:4004/readiness     # → {"ready":true,"db":true,…}

Step 5 — See the data (as Kiran, the procurement officer)

curl -H "x-mock-user: procurement@example.com" ^
  localhost:4004/odata/v4/procurement/PurchaseRequisitions

Expect: 4 purchase requisitions (PR-1001…PR-1004) with statuses. What happened: the x-mock-user header picked your demo identity (Section 7); the READ handler checked your role and auto-added the tenant filter (Section 8–Section 9). Try other-tenant@example.com instead — you'll get an empty list. That's tenant isolation working.

Step 6 — Submit a draft (as Kiran)

curl -X POST -H "Content-Type: application/json" -H "x-mock-user: procurement@example.com" ^
  -d "{\"ID\":\"pr-1004\"}" localhost:4004/odata/v4/procurement/submitRequisition

Expect: "SUBMITTED". PR-1004 moved DRAFT → SUBMITTED (Section 13). Now try the same call as employee@example.com approving it — you'll get 403: employees can't approve (Section 8).

Step 7 — Approve it (as Meera, the approver)

curl -X POST -H "Content-Type: application/json" -H "x-mock-user: approver@example.com" ^
  -d "{\"ID\":\"pr-1004\",\"comment\":\"looks good\"}" localhost:4004/odata/v4/procurement/approveRequisition

Expect: "APPROVED" plus an audit record (Section 15). The state machine, the approval row, and the audit write all happened in one transaction.

Step 8 — Ask the robots (orchestrator, as Sana the manager)

curl -X POST -H "Content-Type: application/json" -H "x-mock-user: manager@example.com" ^
  -d "{\"goal\":\"Create PO for PR-1001\",\"payload\":\"{\\\"requisitionID\\\":\\\"pr-1001\\\",\\\"supplierID\\\":\\\"s-abc\\\"}\"}" ^
  localhost:4004/odata/v4/agents/orchestrate

Expect: {"requiresHumanApproval":true,"policyDecision":"REQUIRE_HUMAN","policy":"PO_EXEC"} — PR-1001 costs ₹12.75L, so policy (Section 12) stops automation and demands a human. No PO is created. This is the system's most important behavior: the AI wanted to act, the policy said no.

Step 9 — Let the robot succeed (small amount)

Create a ₹30,000 PR (number auto-generated), submit it, approve it (steps 5–7 pattern), then orchestrate it. Expect: {"requiresHumanApproval":false,"purchaseOrder":[{…}],"policyDecision":"AUTO_APPROVE"} — a real PO row now exists. Same code path a human uses.

Step 10 — Plug in OpenCode via MCP

Add the snippet from Section 10.3 to opencode.json, run opencode mcp list until cds:MCPService shows connected, then prompt "use the procurement tool to show pending purchase requisitions". Add the catalog block too and ask "is there budget left for department d-it for 1000?" to chat with CatalogService-checkBudget. Every tool call is permission-checked, tenant-filtered and audited — try it as employee@example.com and watch creation tools get denied.

Step 11 — Break things safely (the fun part)

  • Approve an already-approved PR → 409 illegal transition.
  • Fetch with ?tenantId=tenant-b tricks → ignored/denied; you only ever see your tenant.
  • POST an MCP createPurchaseOrder as employee → 403.
  • Create a PR with totalAmount: -5 → 400 validation error.
  • Ask the orchestrator for a rejected PR → requiresHumanApproval with reason (never silently proceeds).

Step 12 — Run everything against real Postgres (Render)

So far you've used throwaway SQLite. The same app runs against real PostgreSQL — same code, same dummy users:

# one-time: secrets already live in gitignored .env + default-env.json
npm run db:deploy:pg   # schema + seeds → Render (cds-deploy CLI can't carry credentials, hence this script)
npm start              # .env sets CDS_ENV=postgres → app connects to Render PG

Expect: identical results — all 18 E2E checks pass, data persists between restarts (unlike SQLite). Flip back anytime: comment out CDS_ENV in .env, restart. Two Postgres realities to know: direct INSERTs need explicit UUIDs (the code does this), and the free cloud DB sleeps — first connection can take ~30s (pool timeouts raised accordingly).

Step 13 — Where to go next in this document

Now re-read Section 4–Section 6 (structure/services) with the running app beside you, then Section 7–Section 12. Terms you don't know → Glossary (the Glossary). When a behavior puzzles you, find its handler in srv/ and its rule in lib/ — the code is organized so every check lives in exactly one obvious place.

3 · Overall Architecture

Every caller — Fiori/UI5, REST, MCP client, AI agent — funnels through authentication → request context → authorization → policy → business logic → PostgreSQL. Agents and MCP never touch the database directly.

flowchart TB U[HUMAN USER] --> A[Authentication JWT / mock] A --> C[RequestContext] C --> Z[AuthorizationService] Z --> O[OData + REST] Z --> AI[Orchestrator Agent] AI --> P[Procurement] & B[Budget] & R[Risk] & I[Invoice] & AP[Approval] P --> M[MCP /mcp/procurement] M --> S[CAP Services] S --> Z2[Authorization + PolicyEngine] Z2 --> BL[Business Logic + Transactions] BL --> PG[(PostgreSQL)] E[External MCP Client e.g. OpenCode] --> M
Design rule: MCP → CAP Service → Authorization → Policy → Business Logic → PostgreSQL. Never MCP → PostgreSQL, never LLM → Database.

5 · Domain Model (CDS)

Concepts: associations vs compositions vs aspects

  • Association = a loose link (foreign key). PurchaseOrders.supplier : Association to Suppliers means "this order points at a supplier that lives its own life". Deleting the order never deletes the supplier.
  • Composition = ownership. PurchaseOrders.items : Composition of many PurchaseOrderItems means "these lines belong to this order" — they are created, read and deleted through the parent (deep insert, cascade delete).
  • Aspect = a reusable stamp. c.TenantAware stamps tenantId onto 20+ entities at once; cuid, managed (from @sap/cds/common) stamp UUID keys and created/modified tracking.
  • CQL/CQN = CAP's query language (a superset of SQL with path expressions like supplier.name instead of JOINs). The MCP query tool accepts CQL SELECT strings — e.g. SELECT from PurchaseRequisitions — which handlers run tenant-filtered.

5.1 Shared aspects — db/common.cds

7 · Authentication — lib/auth/authentication.ts

sequenceDiagram participant C as Client participant A as AuthenticationService participant X as RequestContext C->>A: Bearer JWT ─or─ x-mock-user (+ x-agent-id) A->>A: verify signature · extract sub/zid/roles/agentId A->>X: {userId, tenantId, roles, permissions, actorType, correlationId…}
export interface RequestContext {
  userId: string; username: string; email: string;
  tenantId: string; organizationId?: string; departmentId?: string;
  roles: string[]; permissions: string[];
  isAgent: boolean; agentId?: string; delegatedUserId?: string;
  actorType: 'USER' | 'AGENT' | 'SYSTEM';
  actorId: string; correlationId: string; requestId: string;
}

export function authenticateRequest(req: any) {
  // 1) Real JWT: XSUAA/IAS claims (sub, zid, roles/scope, agentId)
  if (auth?.startsWith('Bearer ')) { verify(token, JWT_SECRET) → build ctx }
  // 2) Safe mock for local dev only (ALLOW_MOCK_AUTH), explicit opt-in header
  const mockUser = headers['x-mock-user'] ?? 'employee@example.com';
  if (headers['x-agent-id']) { isAgent=true; actorType='AGENT'; delegatedUserId=userId }
}

Three identities stay distinct: human (USER), agent (AGENT + agentId), delegated (agent acting for a user → delegatedUserId). Mock users: admin / employee / approver / procurement / manager / finance / auditor@example.com (+ other-tenant@example.com on tenant-b). No passwords exist anywhere — local auth is header-selected identity, production is JWT only.

8.3 Agent authorization — lib/agents/agent-auth.ts

flowchart TB CALL[Agent tool call: agentId + tool + target] --> ID{known agent?} ID -- no --> DENY[AGENT_NOT_AUTHORIZED 403 + audit] ID -- yes --> GRANT{tool in allowedTools?} GRANT -- no --> DENY GRANT -- yes --> PERM{all required permissions held?} PERM -- no --> DENY PERM -- yes --> MCPREQ{holds EXECUTE_MCP_TOOL?} MCPREQ -- no --> DENY MCPREQ -- yes --> ALLOW[execute + audit ALLOW]

Never trust "it's an AI agent". Each agent has a registry entry (tools + permissions) overlaid with DB grants (AgentPermissions, AgentToolPermissions). Example: agent-procurement may createPurchaseOrder; agent-risk may not — enforced per call by authorizeAgentTool(), which throws AGENT_NOT_AUTHORIZED on any gap. A denial aborts the whole task (we removed an early version that swallowed it).

9 · Multi-Tenancy — lib/database/tenant.ts

  • Every tenant-sensitive entity carries tenantId (TenantAware aspect).
  • Tenant is resolved only from the auth context (resolveTenant()); client-supplied tenantId is overwritten on write and filtered on read — enforceTenant() rejects cross-tenant access with 403.
  • Demo tenants: tenant-a (Acme India) and tenant-b (Acme EU, user other-tenant@example.com).
  • Verified live: tenant-b querying PRs gets count: 0 via both OData and MCP.

10 · MCP Interface — six chat servers

Runtime MCP (don't confuse with @cap-js/mcp-server, the dev-time coding assistant). Every domain service is dual-served — OData at its /odata/v4/… path plus Streamable-HTTP MCP at its /mcp/… path (via @mcp: 'name' alongside @odata; a bare @protocol:'odata' would silently suppress the MCP endpoint — a bug we found and fixed). Doc comments on actions become the tool descriptions chat clients show, and @mcp.instructions tells the model how to use each server (describe → query → call, never invent IDs). With cds.mcp: {per_action_tool: true, prefix: true} each action is its own prefixed tool (e.g. CatalogService-checkBudget), so connecting all six servers to one client never collides.

sequenceDiagram participant A as MCP client (OpenCode) participant M as MCP adapter participant H as MCPService handlers participant Z as Authorization+Policy participant D as PostgreSQL A->>M: POST /mcp/procurement (JSON-RPC) M->>H: describe / query / call H->>Z: EXECUTE_MCP_TOOL + tool permission + agent grant + rate limit Z->>D: tenant-filtered business operation D->>H: result H->>A: result + audit + tool-execution record

13 · Workflows & Transactions — lib/workflow/lifecycle.ts

21 · Lessons & Limitations

Hard-won lessons (all verified live)

  • Extend cds.ApplicationService — never raw cds.Service.
  • SELECT.one for single rows; .send() for cross-service actions.
  • after hooks must return data; audit in try/catch.
  • OData functions need /fn(p='v') syntax; ID params as String.
  • @protocol:'odata' suppresses sibling protocols — use @odata @mcp:'x'.
  • PostgreSQL vs SQLite: direct INSERT returns [] on PG (object on SQLite) and generates no UUIDs (service-layer fill_in_keys is bypassed) → always set explicit randomUUID() IDs and re-read by ID.
  • VCAP binding matches by label/tags (@cap-js/postgres wants label postgresql-db); cds deploy --to drops credentials — use an API deploy script with explicit credentials.
  • Cloud Postgres sleeps: raise pool acquireTimeoutMillis (default 1s kills boots) and wake the DB before deploying.
  • Duplicate config sources bite: a plain value in package.json can clobber a .cdsrc.json profile block — mirror [postgres] in both.

Known limitations → next

  • @cap-js/agents is alpha; full Joule A2A handshake needs BTP bindings.
  • In-memory rate limits → Redis for multi-instance.
  • Mock auth is local-only; production needs XSUAA/IAS.
  • AI service is mock-backed until AI Core credentials land.
  • Seed CSVs cover core flows; extend receipt/invoice chains via API.
